# requirements.md: requirement units of the graph library (compact form), functional and non-functional

Each row is one testable requirement in EARS form with one acceptance criterion. Status of every unit:
Approved (akozak, 2026-10-22), except the units added or changed for ontology 2.0 (FR-ONT-01, 05, 06,
FR-READ-10, FR-BLD-07, 09, 15, 20, 26-36, FR-INF-01, 06-08, FR-VER-05, 06) and for the build's own
extraction calls and per-source grounding (FR-LLM-07, 08, FR-BLD-37-41) and for two-pass node
extraction, the hub catalog, known terms and tables (FR-BLD-23, 37, 42-46) and for hub identity and
merging (FR-BLD-15, 17, 25, 47-55) and for trace, the agent reads and findings (FR-ONT-07, 08,
FR-READ-11-22, FR-GAP-01-12): Draft until reviewed.
Verification is by test unless the row says otherwise. Details live in the linked file of each area.

## Core ([architecture.md](architecture.md), [data-model.md](data-model.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-CORE-01 | Every query the library runs shall bind and filter on `project_id`, except schema setup. | Given two projects with equal content, when project A is read or written, then no node or relationship of project B is returned or changed. |
| FR-CORE-02 | `ensure_schema` shall create every constraint and index of the data model and be idempotent. | Given an empty database, when it runs twice, then the second run changes nothing. |
| FR-CORE-03 | If the graph store is older than its supported minimum (Neo4j 5.26, ArcadeDB 26.10, PostgreSQL 15 with pgvector 0.8), then `ensure_schema` shall raise `ConfigurationError`. | Given Neo4j 5.25, when it runs, then `ConfigurationError` (`store_version_unsupported`) is raised and nothing is created. The same check runs per store in its contract and live tests. |
| FR-CORE-04 | When an `OwnedWriter` is asked to write a type its owner does not own, it shall raise `OwnershipError` and write nothing. | Given a `gap` writer, when it upserts a `Module`, then `OwnershipError` is raised. |
| FR-CORE-05 | A write shall change only properties its owner owns. | Given a spec node with a foreign property, when build updates the node, then the foreign property is unchanged. |
| FR-CORE-06 | A `spec_id` shall never change and never be given to a different node of the project. | Given a node deleted in build 2, when build 3 creates a node with another identity key and the same name, then it gets a different `spec_id`. |
| FR-CORE-07 | The library shall never import a host package or read environment variables. | Inspection: the structure test passes. |

## Ontology ([ontology.md](ontology.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-ONT-01 | `load_ontology()` shall load and validate the shipped ontology. | When called without a path, then it returns an ontology (`format_version` 2, version 2.0) with 12 extracted node types and 11 extracted relations. |
| FR-ONT-02 | If an ontology file has problems, then loading shall raise one `OntologyError` listing every problem. | Given a file with an unknown key and an unresolved pair, then the error lists both. |
| FR-ONT-03 | The library shall build a graph from any valid ontology without code changes. | Given the shipped ontology and a fully renamed copy, when one corpus is built with each, then the graphs map onto each other. |
| FR-ONT-04 | `load_ontology` shall merge the ontology files of the installed submodules into one validated ontology. | Given a test submodule file declaring a type owned by build, then `OntologyError` names it; given one with a relation from its type to `Fragment`, then it loads. |
| FR-ONT-05 | If an ontology file's `format_version` is not 2, then loading shall raise `OntologyError`. | Given a file with `format_version: 1`, then the error names the format version. |
| FR-ONT-06 | If a format 2 flag breaks its loader rule, then loading shall raise `OntologyError` naming it. | Given `owner` on a symmetric relation's pair, a `default` pair on a `stated_only` relation and an `otherwise` naming an undeclared relation, then the error lists all three. |
| FR-ONT-07 | The ontology loader shall read `impact` on relations and pairs and apply the checks of [trace.md](trace.md) "Impact roles in the ontology". | Given a symmetric pair `uses` whose reverse pair is also `uses`, then loading raises `OntologyError`. |
| FR-ONT-08 | Merging the gap ontology file shall leave every extraction fingerprint unchanged. | Given the shipped build file alone and with the plan and gap files, then the `nodes`, `edges` and `attributes` fingerprints are equal. |

## Read and search ([api.md](api.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-READ-01 | `node` shall resolve a `spec_id` or any of its aliases to the node. | Given A merged into B, when `node(A)` is called, then B is returned. |
| FR-READ-02 | `find_nodes` shall rank nodes by fused vector and fulltext results. | Given a node matched by both indexes and one matched by one, then the first ranks higher. |
| FR-READ-03 | Where no gateway is available, `find_nodes` shall search fulltext only. | Given a reader without a gateway, then results come from fulltext and say so. |
| FR-READ-04 | `nodes_for_fragment` shall return nodes whose evidence lines overlap the given range. | Given a node grounded on lines 10-12, when lines 12-20 are asked, then it is returned; lines 13-20 do not return it. |
| FR-READ-05 | `impact` shall return nodes reachable within `depth` (1-3) hops, nearest first, at most 500, and flag truncation. | Given 600 reachable nodes, then 500 are returned and `truncated` is true. |
| FR-READ-06 | Read methods shall never return documents, fragments or foreign nodes as spec nodes. | Given a foreign node linked to a spec node, then `nodes` does not include it. |
| FR-READ-07 | `scope` shall return the nodes that reach the given node by a declared spine path, or by a contiguous part of a sequence path, walking symmetric relations either way and never passing through another spine root. | Given a module with a feature holding 2 requirements and a capability it realises grouping 1 requirement, then `scope(module)` returns 5 nodes: the feature, the capability and the 3 requirements. |
| FR-READ-08 | `nodes` and `find_nodes` shall filter by attribute values, and an unknown attribute name shall raise `ConfigurationError`. | Given `where={"is_assumption": "yes"}`, then only assumptions are returned. |
| FR-READ-09 | `find_fragments` shall return `active` fragments whose text matches, from the fulltext index. | Given a retired fragment and an active one containing "SAML", then only the active one is returned. |
| FR-READ-10 | When an attribute with `inherit` is null, readers shall return the owner's value one `via` hop away, without storing it. | Given a requirement without `release` `PART_OF` a feature with `release` "Phase 2", then `node` returns "Phase 2" and the stored property stays absent. |
| FR-READ-11 | `trace` shall walk each edge only in the way its role allows for the direction ([trace.md](trace.md)). | Given `FEAT::CHECKOUT DEPENDS_ON FEAT::CARD_PAYMENT`, then `affects` from card payment has checkout at hop 1 and `based_on` from checkout has card payment at hop 1. |
| FR-READ-12 | `trace` shall never walk a `contains` edge upward, and shall list the seeds' owners up to the first spine root as context. | Given `FEAT::CARD_PAYMENT PART_OF MOD::PAYMENTS_SERVICE`, then the module is in `context` and not in `nodes` unless another relation reaches it. |
| FR-READ-13 | `trace` shall add the members of every reached node that is not a spine root, one hop further, with step `scope`. | Given checkout reached at hop 1, then `REQ::Q::CHECKOUT_SPEED` is at hop 2 with step `scope`. |
| FR-READ-14 | From a spine root, `trace` shall follow only `uses` and `used_by` edges. | Given a `based_on` trace from `ENT::ORDER` that reaches `MOD::ORDERS_DATABASE` over `STORED_IN`, then `ENT::DUAL_STORED`, also stored there, is not reached. |
| FR-READ-15 | With `include_owner`, `trace` shall also start from the seeds' spine-root owners and mark what it reaches first from them `via_owner`. | Given the card payment seeds, then `based_on` at depth 1 returns `IFC::STRIPE_API` with `via_owner` true; with `include_owner` false it returns nothing. |
| FR-READ-16 | With `basis="trusted"`, `trace` shall walk only stated and implied edges. | Given an inferred `DEPENDS_ON` into a seed, then it is not walked by default and is walked with `basis="any"`, carrying its confidence. |
| FR-READ-17 | `trace` shall order nodes by hop then `spec_id`, return at most `limit`, set `truncated`, and give the same answer for the same graph. | Given 30 reachable nodes and `limit` 10, then 10 nodes are returned and `truncated` is true, the same 10 every time. |
| FR-READ-18 | `similar` shall return the spec nodes whose stored vector scores at least `min_score` against a source's, without an embedding call, leaving out nodes linked to a source when `exclude_linked` ([api.md](api.md) "Read and search"). | Given a source with a linked and an unlinked node, both scoring 0.9, and a third scoring 0.7, then with `min_score` 0.75 only the unlinked node is returned with `like` naming the source; with `exclude_linked` false both 0.9 nodes are; the gateway's `embed` is never called; `min_score` 1.5 raises `ConfigurationError` (`invalid_min_score`). |
| FR-READ-19 | `evidence` shall return one item per evidence fragment of the built revision with up to `context_lines` lines before and after the quote and the other nodes on those lines. | Given a node grounded on lines 10-12 of a 13-line document and another node on line 12, then the item has lines 10-12 as `quote`, lines 8-9 as `before`, line 13 as `after` and the other node in `others`; a retired fragment gives no item; an unknown id returns `None`; `context_lines` 6 raises `invalid_context_lines`. |
| FR-READ-20 | `paths` shall return at most 3 shortest chains of at most `max_hops` trusted edges, `based_on` first, else `affects`, with no spine root inside a chain. | Given `FEAT::CHECKOUT DEPENDS_ON FEAT::CARD_PAYMENT`, then `paths(checkout, card payment)` answers `based_on` with one 1-hop chain and `paths(card payment, checkout)` answers `affects`; two features joined only through their module answer no chain and `direction` `None`; `max_hops` 5 raises `invalid_max_hops`. |
| FR-READ-21 | `hops` shall return the fewest trusted edges from the sources to each id within `max_hops`, with no spine root inside the chain. | Given card payment as source, then checkout maps to 1, the source to 0, and a node reached only through `MOD::PAYMENTS_SERVICE` is left out; an inferred edge is not walked. |
| FR-READ-22 | `expand` shall rank nodes by personalised PageRank from the seeds, damped at spine roots and mixed with vector similarity, leave out the seeds and `exclude`, and take items in rank order within `budget_tokens` (characters / 4, rounded up). | Given the shop fixture seeded with card payment and `budget_tokens` 100, then no seed or excluded node is an item, the item tokens sum to `tokens` ≤ 100, `left_out` counts the ranked nodes not taken, and the same graph gives the same items; `budget_tokens` 50 raises `invalid_budget`. |

## LLM gateway and judges ([api.md](api.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-LLM-01 | Every model and embedding call shall go through the process's one gateway and its limiter. | Given concurrency 4, when 10 calls are made, then at most 4 run at once. |
| FR-LLM-02 | When a call hits a rate limit, timeout or server error, the gateway shall retry within the call class budget. | Given two 429 answers then success, then the call succeeds after 3 attempts. |
| FR-LLM-03 | If the endpoint rejects authentication or the model, then the gateway shall raise `LLMFatalError` without retrying. | Given a 401, then one request is sent and `LLMFatalError` is raised. |
| FR-LLM-04 | When an answer does not match the output schema, the gateway shall retry once with a repair note, then raise `LLMError`. | Given two malformed answers, then `LLMError` is raised after 2 requests. |
| FR-LLM-05 | Prompts shall place document text in marked blocks and state that it is evidence, not instructions. | Inspection of every prompt template. |
| FR-LLM-06 | A judge verdict shall be accepted only when its confidence meets the floor and every cited quote occurs in the cited fragment. | Given a verdict quoting text absent from its fragment, then it is rejected. |
| FR-LLM-07 | The build's node and edge extraction calls shall be gateway `structured` calls with the build's own messages and answer schemas, using Chat Completions with JSON-schema output. | Given concurrency 2 and 5 parallel node calls, then at most 2 requests are in flight, every request is a Chat Completions request with a JSON schema, and usage counts all 5 under prompt `nodes.hubs.14`. |
| FR-LLM-08 | The gateway shall count, per call class and prompt name, the input tokens the provider reports as read from its prompt cache. | Given a completion reporting 1,000 input tokens of which 800 cached, then usage shows 1,000 input and 800 cached input tokens; given a completion reporting none, then 0 cached. |

## Build ([build.md](build.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-BLD-01 | When a project has no persisted graph, the library shall choose mode `first` and extract every fragment. | Given an empty project and 3 documents, then all fragments are extracted and persisted. |
| FR-BLD-02 | The build shall derive the change set from the corpus snapshot and the persisted documents. | Given one new, one revised and one missing document, then the change set holds exactly those three. |
| FR-BLD-03 | In an `update` build, only new, changed and retried fragments shall be extracted. | Given one edited section in one of 10 documents, then node extraction runs only on a window over that section's fragments, and every other fragment keeps its stored nodes. |
| FR-BLD-04 | An unchanged section shall keep its fragment id across revisions. | Given a revision that inserts a paragraph in section 2, then sections 1 and 3 keep their ids. |
| FR-BLD-05 | When a revision drops a fragment or a document is removed, its fragments shall become `retired` and nodes supported only by them shall be deleted. | Given a requirement stated only in a removed section, then after the build the node is gone and listed as removed. |
| FR-BLD-06 | Unchanged nodes shall keep their `spec_id` across `update` and `rebuild` builds. | Given a rebuild of an unchanged corpus, then every `spec_id` is the same. |
| FR-BLD-07 | Raw nodes with the same identity key in one identity scope, and hub nodes of one label whose names normalise alike, shall become one node. | Given `FR-ADM-007` extracted as a functional and as a quality requirement, then one node exists; given modules "Orders service" and "Orders Service", then one node exists. |
| FR-BLD-08 | Every persisted spec node and every `stated` or `implied` edge shall be grounded as invariant D4 requires. | Inspection of a built test graph: verification reports no ungrounded node or edge. |
| FR-BLD-09 | An edge whose relation is not legal for its pair shall be legalised or quarantined and counted. | Given an extracted `Module PART_OF Requirement`, then it is flipped or quarantined and `dropped_edges` counts the quarantined ones. |
| FR-BLD-10 | When merging nodes, build shall move every relationship it does not own to the surviving node. | Given a foreign relationship on the losing node, then after the merge it is on the survivor. |
| FR-BLD-11 | If an extraction call fails after its retries, then its dirty fragments shall become `skipped` and the build shall end `partially_succeeded`. | Given a unit whose calls all return malformed output, then its fragments are skipped with an error code. |
| FR-BLD-12 | A changed fragment that is skipped shall keep its last extracted version as support. | Given an edit whose extraction fails, then the nodes of the old text remain. |
| FR-BLD-13 | When persist is interrupted, re-running it shall continue from its cursor without duplicating writes. | Given a failure after batch 3, when persist re-runs, then batches 4+ are applied and the graph equals an uninterrupted run. |
| FR-BLD-14 | An `update` build whose options differ from the frozen options shall raise `ConfigurationError`. | Given a changed `fragment_tokens`, then the update build refuses to start. |
| FR-BLD-15 | The build result shall report status, settled flag, spec changes, quarantine, guard-refused dedup pairs, verification summary and metrics. | Given any finished build, then every field is present. |
| FR-BLD-16 | When the host asks for an estimate, the library shall report the units to extract and the expected calls and input tokens per estimated step without any model call or write. | Given 3 new documents, when the estimate runs, then the gateway records no call, the graph is unchanged, and calls and tokens are reported per step. |
| FR-BLD-17 | Hub nodes (roles `anchor`, `group`) that the documents use for one part of the system or one grouping shall be merged by a block-wise consolidation pass and a pair pass over candidate pairs, never across different explicit ids. | Given hubs "Backend" and "Backend service" that the documents use for one part, then one node exists; given two hubs with different explicit ids, they never merge. |
| FR-BLD-18 | Resolve shall never merge requirements without an explicit id by similarity, and Conform shall merge them only when no deduplication guard refuses. | Given "Export completes within 5 s" and "Export completes within 10 s", then two nodes exist. |
| FR-BLD-19 | Edges with the same edge key shall merge, a symmetric edge being keyed in canonical order. | Given `RELATES_TO` extracted as A to B and as B to A, then one edge exists with the evidence of both. |
| FR-BLD-20 | When a requirement's quote or `stmt` names the explicit id of a requirement with a different owner, build shall add `RELATES_TO` with basis `implied`. | Given "Bulk export reuses FR-012" and FR-012 in another feature, then the two requirements are related with basis `implied`; given both in one feature, then no edge is added. |
| FR-BLD-21 | Each unit's edge catalog shall include relevant hub nodes from the whole project, at most `catalog_limit`. | Given a feature defined in document A and its requirement stated in document B without naming it, then the requirement is `PART_OF` the feature. |
| FR-BLD-22 | An `update` build shall reuse an edge window's stored edges when its content and window catalog are unchanged. | Given a new module in document C unrelated to document B, then B's edges are reused and no edge extraction call runs for B. |
| FR-BLD-23 | The statement pass shall be shown the hub catalog as known terms; in `update` builds the hub pass shall be shown the persisted hub nodes, and the statement pass the persisted hubs merged with the catalog, a persisted name winning over the catalog's. | Given a first build of 3 documents naming "Orders service", then every statement-pass prompt over a unit that names it lists it as a known term; given an `update` whose catalog names persisted hub "Orders service" also "OMS", then the statement pass shows `Orders service (Module; also: OMS)`. |
| FR-BLD-24 | When requirements without an explicit id, of the same label and identity scope, restate one commitment in near-identical words, build shall merge them into one node. | Given the same id-less requirement stated in two documents in slightly different words, then one node exists with a statement from each document. |
| FR-BLD-25 | A consolidation decision stored for a pair of hubs shall be reused by later builds while the evidence it was made on is unchanged. | Given a first build that merged hubs A and B, when an `update` build runs on a corpus where both still exist unchanged, then they stay one node and no consolidation call is made for a block whose pairs are all decided; given A's source fragment edited, then the pair is judged again (`decisions_expired` ≥ 1). |
| FR-BLD-26 | Conform shall store an attribute's declared `default` when its value is null. | Given a module extracted without `in_scope`, then it is stored with `in_scope` "yes" and `nodes(where={"in_scope": "yes"})` returns it. |
| FR-BLD-27 | Conform shall normalise the legal graph in the order of build.md "Normalisation", so that the target graph holds invariants D6 and D7. | Given a requirement extracted `PART_OF` a feature and `PART_OF` two modules, then the target graph gives it one owner and each other edge is converted, dropped or quarantined as the stages say. |
| FR-BLD-28 | An owner conflict shall be won by the lower `owner_rank`, then `stated` over `implied`, then more evidence fragments, then the conform judge; a loser that is the winner's own owner shall be dropped as redundant. | Given a requirement `PART_OF` feature F and `PART_OF` F's module, then only the feature edge remains and no judge call is made. |
| FR-BLD-29 | The conform judge shall be called at most once per conflict group, its verdicts reused for the same input, at most `conform.cap` fresh calls per build; a failed call, a verdict below the floor or a group past the cap shall give the fallback relation. | Given the same input built twice, then the second build makes no conform judge call and gives the same graph; given cap 1 and two judged groups, then one call is made and the other loser becomes `RELATES_TO`. |
| FR-BLD-30 | When a pair's `where` fails, the edge shall become the pair's `otherwise` relation if legal for its ends, else be quarantined with the pair's `where_reason`. | Given a functional requirement `PART_OF` an external module, then it `RELATES_TO` that module; given a feature `PART_OF` an external module, then the edge is quarantined `external_owner`. |
| FR-BLD-31 | A cycle of an `acyclic` relation shall be broken at its weakest edge, which becomes the fallback relation when legal or is quarantined `cycle_broken`. | Given feature A `DEPENDS_ON` B stated in two fragments and B `DEPENDS_ON` A stated in one, then the second edge is quarantined `cycle_broken` without a judge call. |
| FR-BLD-32 | Edges Conform or inference cannot keep shall be listed in the build result's quarantine with reason, relation, labels, `spec_id`s, basis and fragments, and never written to Neo4j. | Given an extracted edge on an undeclared pair, then the quarantine lists it as `illegal_pair`, `quarantine_by_reason` counts it and the graph has no such edge. |
| FR-BLD-33 | If the target graph breaks D6 or D7, then Conform shall raise `ConformanceError`. | Given a normalisation fault that leaves a feature with two modules, then `ConformanceError` is raised before Diff. |
| FR-BLD-34 | Build shall add `derive_via` edges consumer module → provider module through a shared hub with basis `implied`; a stated edge of the same key wins. | Given an interface `PROVIDED_BY` module P and `CONSUMED_BY` module C, then C `INTEGRATES_WITH` P exists with basis `implied`. |
| FR-BLD-35 | A node of a type with `merge_across_labels: false` shall never be merged with a node of another label. | Given an Interface and a Module both named "Payments API" and a stored decision saying they are the same, then two nodes exist. |
| FR-BLD-36 | When an `update` build finds the ontology's labels or relations changed, it shall raise `ConfigurationError("ontology_changed")` naming the migration; after the project's graph is dropped, the next build shall be `first` under the new ontology. | Given a graph built with ontology 1.3 and the 2.0 ontology, then `update` refuses; after the drop, the build is `first` and the graph has only 2.0 labels. |
| FR-BLD-37 | Node extraction shall make two calls per window with a dirty fragment: the hub pass (list `hubs`, each item also with the other names the text uses for it) over every window first, then the statement pass (list `statements`); each item with a name, a label of its list, a quote and fragment numbers. | Given a unit of 2 windows, then 4 node calls are made, the 2 hub calls before any statement call, and usage counts 2 under `nodes.hubs.14` and 2 under `nodes.statements.15`. |
| FR-BLD-42 | An item without fragment numbers inside its window shall be tied to the window fragments whose text holds its quote, else to every fragment of the window. | Given a window of fragments 1-3 and an item with fragments [5] quoting a sentence of fragment 2, then its raw node is tied to fragment 2 (`quote_attributions` 1); given a quote found in none, then it is tied to fragments 1-3 with attribution `window_fallback` and `window_fallbacks` counts it. |
| FR-BLD-43 | The hub pass items shall be merged into the hub catalog deterministically, by label and name and through their aliases, refusing a hub of more than 4 name groups and dropping weak aliases, aliases naming another label's hub and aliases claimed by two or more hubs. | Given items "Image QA Service" with alias "IQS" and "IQS" in another document, then the catalog has one hub "Image QA Service" with alias "IQS"; given alias "Payments" claimed by two hubs, then neither keeps it and `catalog_aliases_dropped` counts it. |
| FR-BLD-44 | Each unit shall be shown every known term its fragments name by name or alias (at most 100), then at most `known_terms_limit` others by cosine to its fragments at 0.40 or above, each with its type and at most 4 aliases. | Given `known_terms_limit` 2, a unit naming 5 hubs and 10 close others, then its known terms are the 5 named and 2 nearby; given a unit naming a hub only by its alias, then that hub is a mentioned term. |
| FR-BLD-45 | Node extraction shall read a table as the sentences it stands for: one statement per row of a requirements, rules, settings, services, environments or integrations table, one entity for a field table of one object, one statement per meaningful matrix cell, and nothing from a table that only lists names, terms or people. | Analysis: on the test corpus, a 5-row requirements table gives 5 statements, a 4 x 6 role-action matrix one statement per non-empty cell group, and a glossary none. |
| FR-BLD-46 | A fragment's node results shall be stored per pass, only when every pass answered it, and reused only when every pass's results are stored. | Given an `update` whose statement call for a dirty fragment fails, then no new node result of either pass is stored for it; given a stored hub-pass result alone for an unchanged fragment, then it is extracted again. |
| FR-BLD-47 | Resolve shall judge as candidate pairs, per label part, each hub with its 5 nearest hubs by a candidate vector of name, heading and quote at cosine 0.52 or above, and every two hubs named by one hub catalog entry, whether or not their names are near. | Given hubs "IQS" and "Image QA Service" far apart on the name chain and a catalog entry naming both, then the pair is judged (in a block holding both, else in the pair pass) and recorded in `pair_candidates`. |
| FR-BLD-48 | Resolve shall cut each label part into consolidation blocks of at most 120 hubs overlapping by 10, and judge candidate pairs no block held in batches of at most 16 hubs of one part, at most 60 batches per build, leaving the rest for the next build. | Given open candidate pairs that fill 65 batches, then the pair pass makes 60 judge calls, `pair_over_cap` counts the pairs left out, and no decision is stored for them. |
| FR-BLD-49 | The hub judge shall be shown, per hub, its label, name, quote, the heading path of its main fragment, up to 3 requirements of that fragment and up to 2 other source lines naming it, all inside untrusted blocks. | Given a hub quoted from a section with 5 requirements, 2 naming the hub, then its line holds the section's heading path and 3 requirements, the 2 naming it first. |
| FR-BLD-50 | A stored hub decision or dedup verdict shall be used only while the evidence hash of both sides matches; otherwise it shall be skipped, counted as expired and judged again. | Given a stored `same` decision for hubs A and B and A's fragment edited, when an `update` runs, then the pair is sent to the judge and `decisions_expired` counts it, while decisions between unchanged hubs are reused. |
| FR-BLD-51 | When the hub judge or the dedup model answers with `low` confidence, the build shall not merge, shall not store a decision, and shall judge the pair again in the next build. | Given a hub group answered `low`, then its hubs stay apart, `unsure_groups` is 1, and the next build sends their block again. |
| FR-BLD-52 | Requirement dedup shall also take as candidates each requirement's 3 nearest by a candidate vector of label, name, `stmt` and quote at cosine 0.80 or above, and never merge such a pair without the guards and a model verdict. | Given two id-less requirements stating one commitment in different words with name cosine below 0.85, then they are a candidate pair (`dedup_candidates_rich_only`), and they merge only on a `same` verdict. |
| FR-BLD-53 | The build result shall list each requirement pair a pairwise dedup guard refused, by `spec_id`, with label, guard and cosines, never by identity key. | Given "Export completes within 5 s" and "Export completes within 10 s", then `dedup_refused` holds one pair with guard `numbers` and both `spec_id`s, and `dedup_refused_by_guard` counts it. |
| FR-BLD-54 | Every hub merge and every hub candidate pair shall be recorded on the resolve artifact with its source and outcome. | Given a build that merges one pair in a block and one in the pair pass, then `merges` holds one `block` and one `pair` merge and `hub_merges_by_source` reports both. |
| FR-BLD-55 | Hub names shall be keyed and matched in one hub form: `.` between letters, `-` and `_` as spaces, upper-case `_` compounds as lower-case words, mixed-case words ending in an upper-case letter or `ops` only case-folded, and English plurals folded with exception lists. | Given modules "order.paid", "ORDER_PAID" and "Order paid", then one node exists; given "Alias service" and "Aliases service", then both key as `alias service`; given "DevOps", then it keys as `devops`. |
| FR-BLD-38 | The node call shall give each node its verbatim quote, and the attributes pass shall not ask for a quote. | Given a node call answering a requirement with a quote, then the raw node holds that quote and the attributes call's answer schema has no `quote` field. |
| FR-BLD-39 | Edge extraction shall make one call per edge window (at most 8 per unit, each seeing the whole unit and its catalog) that names catalog entities by name and gives each fact verbatim; a fact naming an entity outside the catalog shall be dropped and counted. | Given an answer linking a catalog entity to a name not in the catalog, then no raw edge is made and `unknown_name_edges` is 1. |
| FR-BLD-40 | Conform shall ground a node in each of its source quotes within that quote's own fragments, so that a node stated in several documents keeps evidence from each. | Given requirement `FR-7` stated in two documents in different words, then the node has evidence lines and a statement in both documents and `unsnapped_source_quotes` is 0. |
| FR-BLD-41 | When a source document of a node stated in several documents changes or is removed, the `update` build shall update the node and keep the evidence of its other sources. | Given a constraint stated in documents A and B and B's sentence reworded, then Diff updates the node with B's new statement and keeps A's; given B removed, then the node remains with A's evidence only. |

## Inference ([analysis.md](analysis.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-INF-01 | Where inference is on, the build shall run each ontology inference rule once after persist, in the file's order. | Given 3 rules, then each is run once per build, in file order. |
| FR-INF-02 | Inference shall read only `stated` and `implied` edges when choosing subjects and candidates, except the inferred edges a rule's `reads` names and inferred owner edges (one owner per node). | Given an orphan attached by inference earlier, then it is still a subject. |
| FR-INF-03 | Inference shall write an edge only for a verdict at or above the floor with valid quotes. | Given a verdict with confidence 0.6, then no edge is written. |
| FR-INF-04 | The new inferred set shall replace the old one in one transaction. | Given a crash during the swap, then the previous inferred edges are intact. |
| FR-INF-05 | If a judge call fails or a verdict is invalid, then the build shall still succeed; if inference fails for any other reason, then the build shall fail and keep the previous inferred edges. | Given a judge that always fails, then the build status is unaffected; given an endpoint that rejects the credentials during inference, then the build is `failed` and the inferred edges are unchanged. |
| FR-INF-06 | An `attach_orphan` subject shall have no target on any owner pair and not match `exclude_where` itself or through its owner; its candidates shall come only from its legal owner labels. | Given a data requirement without an owner, then it is not a subject; given an integration requirement without an owner, then its candidates are modules only. |
| FR-INF-07 | `INF-CONT-02` shall attach a feature without a module to one module. | Given a feature with no module and a verdict naming an internal module, then the feature is `PART_OF` it with basis `inferred`. |
| FR-INF-08 | Every inference proposal shall pass the shared validator against the current graph and the proposals accepted before it; a failing proposal shall be `invalid`, not written, and quarantined `invalid_proposal`. | Given a verdict that would give a feature an external module, then no edge is written and the quarantine lists it. |

## Findings ([gap.md](gap.md))

| ID | Requirement | Acceptance |
|---|---|---|
| FR-GAP-01 | `Findings.add` shall write an open `Finding` with origin `agent`, an `ABOUT` edge per `about` node and a `REFERS_TO` edge per reference, one `ExternalRef` per (project, type, value). | Given two findings citing the same commit, then each is `ABOUT` its nodes and both refer to one `ExternalRef`. |
| FR-GAP-02 | `Findings.add` shall store `about` ids resolved through aliases, and if an id resolves to no node, raise `FindingError("node_not_found")` naming it and write nothing. | Given A merged into B, then `about=[A]` stores `[B]`; given an unknown id, the error names it and no node is written. |
| FR-GAP-03 | When an open finding has the same author, kind, `about` set and normalised text, `Findings.add` shall return it with `created` false and write nothing. | Given an open finding, when the author adds it again with `about` in another order and the text in other case and spacing, then the same `finding_id` returns; after it is resolved, the same add creates a new finding. |
| FR-GAP-04 | `Findings.add` shall enforce the limits of text, `about`, `refers_to` and open findings per author and story, before any write. | Given 50 open findings of one author and story, then the 51st raises `finding_limit`; given 2001 characters of text, then `invalid_text`. |
| FR-GAP-05 | `Findings.add` shall accept only `refers_to` values of the forms in [gap.md](gap.md) "Rules", and never fetch one. | Given a URL with user info, a file path with `..` and a 6 hex commit, then each raises `invalid_ref` before any query; with a recording HTTP client/socket guard, adding a `url` and a `pr` URL makes no network call. |
| FR-GAP-06 | `resolve` and `dismiss` shall close only an `open` finding, recording who, when and the note. | Given a resolved finding, when it is dismissed, then `FindingError("wrong_state")` is raised and it is unchanged. |
| FR-GAP-07 | `Findings.refresh` shall set `orphaned` on an open finding whose `about` id resolves to no node, keep the finding, and clear it when the node is back. | Given a finding about a requirement a build deletes, then after the refresh it is open and `orphaned` with the id kept; after a build restores the requirement, `orphaned` is false and `ABOUT` is restored. |
| FR-GAP-08 | Findings shall never be read by a build or a plan run, and `graph.gap` shall never write a spec node, edge, document or fragment. | Given one project with findings and one without, then an `update` build and a plan run give equal results; an `OwnedWriter` for `gap` refuses a spec label. |
| FR-GAP-09 | A blocking finding shall block the claimed story's tasks with the mapped reason and `blocked_by`, end the claim, and its resolution or dismissal shall unblock the tasks still blocked by it. | API test: given a held story and a blocking `question` about a node a claimed task implements, then the tasks are `blocked` with `spec_ambiguous` and the finding id; after the finding is resolved they are `pending`. |
| FR-GAP-10 | When the plan refuses the block of a new blocking finding, the host shall withdraw that finding. | API test: given a story released between the guard and `block_story`, then the call answers `claim_mismatch`, no finding exists and no task changed. |
| FR-GAP-11 | `open_counts` shall count open findings per asked id, and `findings` shall list blocking findings first, then newest first. | Given two open findings about X and a resolved one, then `open_counts([X])` is `{X: 2}`; given a blocking and a newer non-blocking finding, the blocking one is listed first. |
| FR-GAP-12 | Logs and errors of `graph.gap` shall never contain finding text, notes or `refers_to` values. | Log-capture test over add, resolve, withdraw and refresh. |
